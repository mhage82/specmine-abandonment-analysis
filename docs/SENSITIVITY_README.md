# Abandonment screening sensitivity analysis

This experiment varies only the inactivity threshold (30, 60, 90, 180 days by default). It runs the existing pipeline using one prepared dataset and the same saved review labels.

## Setup

Use the project's Python environment with the completion and figure requirements installed:

```
python -m pip install -r reproducibility/requirements-completion.txt -r requirements-figures.txt
```

The commands below assume `python` is that environment's interpreter. On Windows without activation, replace `python` with `.\.venv-completion\Scripts\python.exe`. Commands must run from the repository root.

Prepared input: `results/abandonment_full_check_01/stage1/specifications.parquet`. If starting from raw data, follow the root and screening README instructions to obtain the pinned dataset and run preparation first. The dataset revision used in the study is `9fbb61541046cb2fb770fa944192a3fc0b64a9b1`. This runner hashes the prepared file; it does not independently certify that raw dataset revision.

## One-command experiment

```
python src/run_abandonment_sensitivity.py --stage1-dir results/abandonment_full_check_01/stage1 --labels docs/reviewed_labels.json --output-dir results/abandonment_sensitivity_01
```

Do not create the output directory first. The runner refuses to overwrite an existing directory. On failure, logs and partial results remain for diagnosis; retry with a new output name. Successful completion is recorded by `sensitivity_manifest.json`, written last.

Optional `--evidence FILE` supplies identical supplemental evidence to every run. Do not pass targeted development labels as evidence. Optional `--thresholds 30 60 90 180` and `--reference-days 90` control the comparison; thresholds must be unique positive integers and include the reference.

## Outputs

- `days_30/screening/`, `days_60/screening/`, `days_90/screening/`, `days_180/screening/`: original pipeline outputs, including manifests and evaluation JSON.
- `days_*.log`: execution output and any errors.
- `sensitivity_summary.csv` and `.json`: counts, percentages, exact candidate additions/removals relative to the reference, and both rules' reviewed-case metrics.
- `threshold_comparison.png` (300 dpi) and `.pdf`: counts across thresholds, including the explicit-status baseline.
- `reviewed_case_comparison.csv`: existing evaluation cases, outcomes, predictions, categories, and unchanged review evidence/rationales at each threshold. Unresolved cases remain excluded from classification metrics. Omitted if there are no evaluation cases.
- `captions.md`, `report.md`: caption and numerical summary with interpretation limits.
- `sensitivity_manifest.json`: input/source/output hashes, interpreter/package versions, commands, and comparison settings. Paths describe the machine that ran the experiment; executable code contains no private machine paths.

The runner verifies output hashes and counts, recomputes evaluation from saved predictions and labels, requires identical input hashes and identifiers, checks that the explicit-status baseline is unchanged, and requires nested candidate sets as thresholds increase. It detects input or source changes during execution.

## Interpretation and error analysis

This is sensitivity of screening volume, not diagnostic sensitivity (recall). Do not select a supposedly optimal threshold from the small, repeatedly used review subset. With no resolved positive examples, recall remains undefined. Undefined metrics are JSON null / empty CSV cells. No-rule-trigger records are not established negatives in the full dataset.

Use the reviewed-case comparison to discuss existing false positives and unclear outcomes. The separately saved targeted template case remains development evidence and is not added to this evaluation. Per-run `review_sample.json` files are generated by the existing pipeline but are not new reviewed cases and are not used by this experiment.

## Verification

```
python -m unittest discover -s tests -p "test_abandonment_screen.py" -v
python -m unittest discover -s tests -p "test_abandonment_sensitivity.py" -v
```

Validation included seven screening tests and two sensitivity-analysis tests, all of which passed. The sensitivity integration test uses synthetic data to verify threshold-dependent predictions, candidate-set changes, exclusion of unresolved labels, figure generation, and overwrite protection. A separate test verifies rejection of inconsistent input hashes.

The sensitivity runner also completed successfully on 28,583 specification records across 415 repositories using the existing saved review labels. Candidate counts were 1,784, 1,128, 742, and 128 at the 30-, 60-, 90-, and 180-day thresholds, respectively. The explicit-status baseline remained at 12 records. Comparison tables, figures, reviewed-case outputs, and the provenance manifest were generated successfully. These checks verify implementation consistency and reproducibility; they do not establish abandonment-detection accuracy.
